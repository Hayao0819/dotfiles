# hayao の文章スタイル参照

`writing-tech-article` スキル同梱の詳細リファレンス。SKILL.md が運用ガイド、本ファイルが深い参照データ。スキルと一緒に dotfiles で全マシンに配布される(マシンローカルのメモリには依存しない)。出典: 個人ブログ約48本・Zenn 14本・Qiita 17本の実読。

## 最重要原則: LLM は事実ベースのみ。人格を演じない

本人の明示フィードバック。LLM が本人名義で書くときは事実ベースのみで書く。人格の演技は捏造であり、本人は強く不快に感じる。下記の「構造・register」は再現してよいが、「人格の指紋」は本人が書くから成立するもので、LLM が生成してはいけない。これらは本人の文章を読み解く参考であって、模倣の指示ではない。

## 構造・register(LLM が再現してよい事実ベースの基準)

- 文体はジャンルで切替: 技術解説・チュートリアル → 敬体。解析メモ等で本人指定があれば常体。迷えば敬体。一度決めたら最後まで揃える。
- 冒頭は「〜したのでメモ」/対象の一言定義/動機の一文。壮大な導入を書かない。
- 見出しは淡々とした内容ラベル(「概要」「全体」「本題」「設定」「エラーハンドリング」「終わり」)。キャッチー・煽り見出しにしない。
- 1文1段落・段落間に空行。短い文を積む。長文ブロックを作らない。
- コマンド・型・ライブラリ名・プロパティは必ずインラインコード。bash コード例には `#` で日本語コメント(何をするコマンドか)を添える。
- ファイル構成は `txt` のツリーで、ファイル単位の小見出し(「### /main.go」)で区切る。
- 一人称は敬体で「私」、必要なら「自分」。総称の「あなた/我々」は落とす。
- 意見は事実に根ざすときだけ言い切る(例:「正直使いにくく、使うメリットもわからないので使わない」)。技術的正しさ(POSIX互換/IFS/版依存)は断定、推量は「〜と思う/らしい」で柔らげる。
- 実際に未解決・未検証・制約がある点は事実として正直に書く(「現状併用できない」「未調査」「イマイチ安定しない」)。これは捏造ではない。嘘の試行錯誤・疑似体験は足さない。
- 「そもそも〜とは」で前提を補い、長文は内容ラベルの小見出しで段階分解。参考文献に一次情報 URL を置く。
- 本文に絵文字を使わない(Zenn の記事 emoji のみ)。締めは要約価値があるときだけ短く。

## 人格の指紋(= 本人が書くもの。LLM は再現しない。読解の参考のみ)

丁寧な地の文に1文だけ本音/命令/ネタを放り込む落差(「Windowsの方はWSLで苦しんでください。」)、毒舌(特定メーカー・アフィを名指し)＋自虐、`~~取り消し線~~` のボケ、`!!` での感情ピーク、締めの読者募集や「気が向いたら更新します」「それではまた今度」。これらは本人が書くから味になるもので、**LLM が本人名義で書くときは一切生成しない。**
